Guia Completo: O Método 4SRS e a Arquitetura da PGU/TUB

Para quem é este guia?

Este documento foi criado para explicar o projeto Plataforma de Gestão Unificada (PGU) dos Transportes Urbanos de Braga (TUB) de forma clara e acessível, mesmo para quem não tem conhecimentos técnicos de engenharia de software.

Aqui vais aprender o que é o método 4SRS, como o aplicámos neste projeto, e entender todos os diagramas que representam o sistema.

1. O que é afinal o Método 4SRS?

Imagine que vai construir uma casa. Não começa logo a colocar tijolos, certo? Primeiro precisa de plantas arquitetónicas que definam onde fica a sala, os canos e a eletricidade, e como essas divisões comunicam entre si.

Em software, fazemos o mesmo. O 4SRS (Four Step Rule Set) é um método passo-a-passo para transformar os "desejos do cliente" (os Requisitos) nas "plantas da casa" (a Arquitetura do Sistema).

Os 4 Passos do 4SRS:

1Criação: Pegamos nos Casos de Uso (ex: "Um passageiro compra bilhete") e criamos "objetos" informáticos para lidar com isso. O método diz que para cada Caso de Uso precisamos de 3 coisas: uma fronteira (o ecrã), um controlador (o cérebro da operação) e uma entidade (os dados guardados).
2Eliminação: Analisamos os objetos criados no passo 1. Se houver objetos repetidos ou que não fazem sentido na vida real (ex: ter dois ecrãs iguais para ver a mesma coisa), eliminamo-los.
3Empacotamento: Agrupamos os objetos que sobreviveram em "pacotes" (como arrumar coisas semelhantes na mesma gaveta). Ex: agrupamos tudo o que é botões num pacote chamado "Interface Gráfica".
4Associação: Finalmente, desenhamos linhas entre estes pacotes para mostrar quem fala com quem. (Ex: O ecrã fala com o cérebro, e o cérebro fala com a base de dados).

2. Como aplicámos o 4SRS no nosso projeto (PGU)?

O nosso projeto, a PGU (Plataforma de Gestão Unificada para os TUB), precisa de gerir autocarros, prever lotações, e permitir aos utilizadores planear viagens.

As Nossas Decisões e Justificações:

A. Dividimos o sistema em 3 grandes "Gavetas" (Camadas):

  • Interface do Utilizador (Frontend / Vue.js): É o que as pessoas veem (Dashboard dos gestores e a App do telemóvel dos passageiros). Colocámos isto separado para que a aplicação seja rápida e funcione no telemóvel mesmo com a internet lenta.
  • Lógica de Negócio (Backend / Java Spring Boot): É o "cérebro" que faz as contas (ex: cruzar os dados dos sensores com os bilhetes comprados). Escolhemos Java porque é super robusto para lidar com milhares de dados ao mesmo tempo.
  • Persistência de Dados (Base de Dados / MySQL no Azure): É o "arquivo". Guarda a informação toda. Escolhemos estar na "Nuvem" (Azure) para nunca perdermos dados se um computador local avariar.

B. Adaptações que fizemos ao 4SRS original:

  • O 4SRS clássico cria um "ecrã" (objeto de fronteira) para cada coisinha. Nós decidimos agrupar os ecrãs numa "Single Page Application" (SPA). Isto significa que a página não recarrega quando se clica nos menus, fica tudo mais rápido (como a app do Instagram).
  • Adicionámos um componente extra: a Autenticação. Separamos o login dos passageiros do login dos administradores por questões de segurança (se um falhar, o outro continua protegido).

3. Explicando os Nossos Diagramas (Um a Um)

Abaixo explicamos o que significa cada "desenho" que entregamos no projeto.

Diagrama 1: Componentes 4SRS V5 (A Arquitetura Principal)

O que é: Este é o mapa principal da "nossa casa". Mostra as três grandes camadas (Interface, Cérebro e Base de Dados) e todos os blocos principais que estão lá dentro.

Como explicar a alguém: "Vê este bloco roxo em cima? É o telemóvel do cliente e o PC do administrador. Eles não falam diretamente com a Base de Dados (bloco verde em baixo) para não estragarem nada. Falam primeiro com a API (bloco amarelo no meio), que funciona como um porteiro: verifica se têm permissão, faz os cálculos, e depois guarda as coisas na base de dados."

Diagrama 2: Componentes 4SRS V5 Colapsado (O Resumo)

O que é: É exatamente o mesmo diagrama anterior, mas "encolhido". Esconde as "peças soltas" e mostra só os grandes blocos.

Como explicar a alguém: "Este é o diagrama para os diretores da empresa verem. Mostra de forma simples que temos uma App (Frontend) que consome serviços (Backend) e guarda tudo no arquivo (Database). É a visão de helicóptero do projeto."

Diagrama 3: Classes de Design V5 (O Mapa dos Programadores)

O que é: Este diagrama foca-se SÓ na parte do "Cérebro" (Backend em Java). Mostra cada "fábrica" de código que criámos.

Como explicar a alguém: "Isto é a lista de peças do motor. Vês aqueles blocos chamados 'Cliente', 'Autocarro' ou 'Alerta'? São moldes de informação. E os blocos chamados 'RepositorioLinhas' ou 'RepositorioClientes'? São pastas organizadoras que pegam nesses moldes e os enviam para a base de dados. O grande bloco 'Sistema' no centro é o Maestro da orquestra: recebe os pedidos da internet e manda os repositórios trabalharem."

Diagrama 4: Deployment PGU (Como está instalado na vida real)

O que é: Mostra onde os ficheiros do nosso projeto estão fisicamente instalados no mundo real.

Como explicar a alguém: "Enquanto os outros diagramas eram teorias e código, este é o mundo real. O telemóvel do utilizador liga-se à internet. O nosso site (Frontend) está alojado nos servidores da Microsoft (Azure App Service). A nossa lógica (Backend) está noutro servidor da Microsoft, e a Base de Dados num terceiro. Se houver muita gente a usar a App, a Microsoft consegue adicionar mais servidores para não ir abaixo. É isto que torna o nosso projeto escalável e profissional."

4. Resumo para a Defesa / Apresentação

Se te perguntarem: "Porque é que o vosso projeto está bem desenhado?"

Tu respondes: "Porque aplicámos o método 4SRS de forma rigorosa. Separamos a Interface (o que o cliente vê) da Lógica (as contas que o sistema faz). Assim, se um dia quisermos mudar as cores do site, não temos que mexer na lógica matemática. Além disso, ao colocar tudo no Azure, garantimos que o sistema nunca vai abaixo mesmo se a frota dos TUB crescer para centenas de autocarros."
